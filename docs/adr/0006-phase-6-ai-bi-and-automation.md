# ADR 0006 — Phase 6 AI, BI & automation decisions

Status: accepted · 2026-11-26

| # | Decision | Why |
|---|---|---|
| 1 | **Certified metric definitions in code**, each with an id and version (`finance-v1`, `disease-v1`, `operations-v1`) and a written definition shown next to every value. The accounting summary and the AI layer call the same `computeFinance`, so AI totals cannot drift from the official report. | Spec §5.29 "metric definitions versioned", §5.30 "AI totals match official report". |
| 2 | **Immutable snapshots.** A snapshot stores one month's facts with a SHA-256 fingerprint of their canonical form. Capturing again on unchanged data returns the same snapshot; a late correction creates version n+1 that names the one it supersedes. Integrity (stored facts vs fingerprint) and freshness (fingerprint vs live data) can be checked at any time. | Spec §5.29 "re-run report produces same numbers on same source snapshot", §9.3 "track late coding corrections". |
| 3 | **Disease counting** follows §9.3 exactly: confirmed diagnoses only, unique patients per ICD-11 code per month in the hospital time zone, merged records counted once, encounter counts and newly-diagnosed counts separate, suspected cases reported apart and never added. Any count from 1 to 4 is suppressed (`<5`). Snapshots hold no patient identifiers. | Spec §5.31 "no population prevalence claims", §5.29 "suppress small sensitive cohorts". |
| 4 | **AI is read-only and separate from calculation.** The metrics engine produces facts (including month-on-month changes and shares); a narrative provider only words them using server-side, versioned templates. Every number in the text must be the formatted value of a fact the sentence cites, checked in code; a draft that fails cannot be reviewed. Every sentence lists its metric ids; the page states the text is AI-written. | Spec §9.1, §9.6, §9.7. |
| 5 | **The built-in narrative provider is deterministic and runs on the server**, so no patient or financial data leaves the hospital. Providers sit behind one interface, so an external language model can be added later under the same number check, once the hospital decides on data-transfer terms. | Spec §9.7 "respect jurisdictional data transfer terms". |
| 6 | **Review before release.** Finance summaries: Generated → Reviewed (finance) → Published by a different finance person with recent MFA. Disease summaries: Generated → Validated (clinical safety) → Reviewed (clinical governance), different people. Every step re-checks the source snapshot's fingerprint; released summaries are frozen. | Spec §5.30, §5.31 workflows. |
| 7 | **Hospital 360** is built only from snapshots and follows the §9.5 sections; every figure cites metric id and snapshot; missing measures say why. Finance and clinical sections are signed by qualified people (never one person for both), the owner approves and publishes with recent MFA; the published content is fingerprinted and HMAC-signed. Corrections are new versions that supersede the old one, which stays readable. Export is a manifest with fingerprint, signature and sign-offs, audited. | Spec §5.32, §9.8 checklist. |
| 8 | **Forms studio has no code.** Six field types and two rule types (who fills the form in, who approves a submission); keys are checked against reserved names; answers are validated on the server and unknown fields refused. Draft → Tested (with a sample) → Approved (not by the designer; high-risk forms need the clinical safety officer first) → Published; the previous version retires. Submissions keep their form version and are always shown with that version's fields; publishing a retired version rolls back. | Spec §5.33 "no arbitrary code execution; reversible; versioned form keeps reading historical submissions". |

## Not done in Phase 6
- Scheduled monthly builds (reports are built on request; a scheduler belongs with Phase 7 operations).
- PDF/Excel rendering on the server (the report prints to PDF from the browser; the signed JSON manifest is the archival export).
- Forecasting, scheduling and stock-demand models, the clinical-notes assistant and the radiology assistant (§9.2) — each needs validated models and clinical sign-off.
- Workflow triggers beyond submission approval (notifications, task creation).
- Quality incidents, readmission measures and budgets are shown as unavailable until those modules exist.
